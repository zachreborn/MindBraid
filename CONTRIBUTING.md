# Contributing to MindBraid

Thanks for helping improve MindBraid. Please read [AGENTS.md](AGENTS.md) first:
it describes the product contract (what the plugin may and may not change in a
note) and the architecture boundaries that every change must respect.

## Before you open a pull request

Run the repository checks and make sure they pass:

```sh
npm run check
git diff --check
```

`main.js` is generated by esbuild. Commit the regenerated file together with the
source change that produced it, and never edit it by hand. The browser visual
regression tests (`npm run test:visual`) use Linux baselines and run in CI.

## Commit messages and releases

Releases are generated from [Conventional Commits](https://www.conventionalcommits.org/)
that reach `main`, so the commit message type decides whether a change is
released and where it appears in the release notes:

- `feat:` is a user-facing feature and is listed under **Added**.
- `fix:` is a bug fix and is listed under **Fixed**.
- `perf:` and `revert:` are listed under **Changed**.
- `docs:`, `style:`, `refactor:`, `test:`, `build:`, `ci:`, and `chore:` do not
  appear in release notes and do not trigger a release on their own.
- A `!` after the type, or a `BREAKING CHANGE:` footer, marks a breaking change.
- Changes that only touch `promo-site/` or the promo-site deploy workflow never
  trigger a plugin release.

While the version is below 1.0.0, `feat:` and `fix:` both produce a patch
release (for example 0.1.5 to 0.1.6) and a breaking change produces a minor
release.

When a pull request is merged with a merge commit, every commit in the branch
is read. When it is squash merged, the pull request title becomes the commit
message, so write the title as a Conventional Commit.

### How a release happens

1. Conventional Commits land on `main`.
2. The **Release Please** workflow opens or updates a release pull request that
   bumps the version in `package.json`, `package-lock.json`, and
   `manifest.json`, and prepends the new entry to `CHANGELOG.md`. CI is run on
   that pull request.
3. A maintainer reviews and merges the release pull request. Release Please
   then creates the tag (for example `0.1.6`, without a `v` prefix) and a
   draft GitHub Release.
4. The **Create draft release** workflow builds the plugin from that tag,
   verifies it, attests `main.js`, `manifest.json`, and `styles.css`, and
   attaches them to the draft.
5. A maintainer reviews the draft and publishes it. Obsidian users receive the
   update only after the release is published.

Do not edit version numbers or `CHANGELOG.md` by hand; Release Please owns them.

### When a release raises the minimum Obsidian version

`versions.json` is Obsidian's fallback table for users on an older app, and it
only needs a new entry when `minAppVersion` in `manifest.json` changes. If a
release raises `minAppVersion`, CI on the release pull request fails with a
message asking for an entry. Add `"<new version>": "<new minAppVersion>"` to
`versions.json` on the release pull request branch. Release Please may rebuild
that branch when more commits land on `main`, so re-check CI before merging.
